# Channel Members And Global Coordinator Design

- Status: Design approved for documentation
- Date: 2026-06-09
- Product area: Channels, coordinator routing, channel membership, agent memory, desktop chat UI

## Summary

Slei should use one shared system Agent, `agent_global_coordinator`, to coordinate
all channels. The coordinator remains a real product Agent, but it is internal:
it is not shown in member lists, cannot be selected by users, cannot receive
direct messages, and cannot be chosen as a downstream route target.

Channels should expose a conventional IM-style member list on the right side of
the chat workspace. The list is collapsed by default and can be expanded from the
chat header. Users can view, add, and remove existing Agents from the active
channel. Membership changes update Agent memory. New members also generate a
visible personalized join report after their memory update succeeds.

This slice is intentionally lightweight. It does not add a separate membership
snapshot table or migrate channel membership into SQLite. Whenever coordinator
routing or memory maintenance needs channel context, the daemon builds a fresh
context package from the current channel members and current Agent records.

## Goals

- Replace per-channel coordinator Agents with one shared `agent_global_coordinator`.
- Keep the coordinator as a real system-owned Agent.
- Hide all coordinator Agents from user-facing member, mention, direct-message,
  and member-selection surfaces.
- Build coordinator prompt context from the current channel roster at routing
  time.
- Add a collapsible right-side channel member list in Chat.
- Let users add existing ordinary Agents to a channel.
- Let users remove ordinary Agents from a channel without deleting the Agent.
- Run memory updates after channel membership changes.
- Trigger a personalized visible join report for newly added members only.
- Make member and channel delete buttons safe: hover/focus reveal, red icon,
  right aligned, vertically centered, and confirmed through a popover.

## Non-Goals

- Do not build a membership snapshot/version table in this slice.
- Do not migrate file-backed channel state into database-backed channel state.
- Do not allow creating brand-new Agents from the channel member list.
- Do not show or route work to coordinator Agents.
- Do not make removed members or remaining members post visible removal reports.
- Do not delete Agent records when removing them from a channel.

## Confirmed Decisions

| Topic | Decision |
| --- | --- |
| Coordinator identity | One system Agent: `agent_global_coordinator` |
| Coordinator visibility | Hidden from user-facing member, DM, mention, and selection UI |
| Coordinator routing target | Never valid as a downstream target |
| Membership context | Built live from current channel members and Agent records |
| Member management UI | Right-side Chat member list, collapsed by default |
| Add member source | Existing ordinary Agents only |
| New member report | Generated by the newly added Agent after memory update |
| Remove member memory | Update both the removed Agent and remaining channel Agents |
| Remove member report | No visible report |
| Channel delete control | Hover/focus reveal, red icon, confirmation popover |

## Coordinator Model

The daemon should expose a single system-owned product Agent with:

- `id`: `agent_global_coordinator`
- `agentKind`: `coordinator`
- `systemOwned`: `true`
- `directMessageEnabled`: false in desktop projections

New code should stop creating or depending on per-channel coordinator Agents such
as `agent_coordinator_all` or `agent_coordinator_dev`. Existing legacy
coordinator records may remain on disk for compatibility, but every user-facing
and routing-target filter must treat both legacy per-channel coordinators and the
new global coordinator as internal.

Coordinator worker sessions should use `agent_global_coordinator` as the
runtime `agent_id`. The session input still includes the active channel id and
channel name, so the same coordinator Agent can make channel-specific decisions.

## Coordinator Context

The lightweight approach builds context live. When `ChannelOrchestratorService`
starts a coordinator run, it should:

1. Read the active channel record.
2. Read current channel membership state.
3. Read current product Agent records for those member ids.
4. Drop all coordinator Agents from the routable roster.
5. Add each ordinary member to the prompt with:
   - agent id
   - name
   - handle
   - role or description summary
   - agent kind
   - readiness
6. Add current channel project paths/workspace mounts.

The prompt should continue to tell the coordinator to return JSON only, never
answer visibly, and choose only non-coordinator channel members as downstream
targets. The validator must reject any target whose Agent is `agentKind:
"coordinator"` or whose id is a known coordinator id.

## Coordinator Filtering

Filtering must use a shared helper rather than scattered prefix checks. A member
is internal if either:

- its Agent record has `agentKind === "coordinator"`, or
- its id matches legacy coordinator ids such as `agent_coordinator_*`, or
- its id is `agent_global_coordinator`.

Internal coordinator Agents must be excluded from:

- desktop member pages and channel member lists
- direct message lists and direct-message creation
- composer mention suggestions
- create-channel Agent selection
- add-channel-member Agent selection
- coordinator routing target validation
- visible channel member counts

The coordinator prompt roster should exclude coordinator Agents entirely. This
reduces the chance that the model selects the coordinator as a target.

In this spec, "ordinary Agent" means a non-coordinator Agent eligible for channel
membership and user-directed collaboration.

## Channel Member UI

The Chat workspace should gain a right-side channel member list. It is collapsed
by default. A member button in the chat header toggles it. When expanded, the
main chat area gives space to the right column; when collapsed, chat uses the
full width.

The right member list shows only ordinary members in the active channel. Each row
should show:

- avatar
- display name
- handle
- role or description summary
- readiness badge
- hover/focus delete affordance

The top of the member list contains an add button. Adding opens a compact picker
for existing ordinary Agents that are not already in the channel. Coordinators
are never selectable. Confirming an Agent starts the add-member flow.

## Member Add Flow

Adding a member should be an API-backed operation, not only local UI state.

Daemon behavior:

1. Validate that the channel exists.
2. Validate that the selected Agent exists and is not a coordinator.
3. Add the Agent to the channel if not already present.
4. Set readiness to `joining` for new membership.
5. Record a memory update request.
6. Run or enqueue the memory-maintainer update for that Agent.
7. When memory update succeeds, set readiness to `ready`.
8. Start the newly added Agent to generate a short personalized join report.
9. Persist the generated report as a visible Agent message in the channel.

The join report is Agent-authored. It should not be a daemon-fixed string. The
runtime context should ask for a short self-introduction that says what the Agent
is responsible for and when users or other Agents should mention it. It should
not promise to start unrelated work.

If memory update fails, the member moves to `memory_failed` and no join report is
started. If the join report run fails after memory succeeds, the member can stay
`ready`; the daemon records a diagnostic event and the UI may expose a retry
later.

## Member Remove Flow

Removing a member removes the Agent from the active channel only. It must not
delete the Agent itself.

Daemon behavior:

1. Validate that the channel exists.
2. Validate that the target Agent is an ordinary Agent.
3. Remove the Agent from the channel membership.
4. Update the removed Agent's memory so it no longer treats the channel as an
   active membership.
5. Update the remaining ordinary channel members' memory so their roster no
   longer includes the removed Agent.
6. Do not start visible Agent report messages.

Deletion should be best-effort after membership removal. A memory update failure
should be visible through readiness/diagnostics, but it should not recreate the
removed membership.

## Channel Sidebar Delete Control

The channel sidebar delete button should be part of the channel row hover/focus
area. It should be vertically centered, aligned to the far right, hidden by
default, and visible on row hover or keyboard focus within the row. The icon
should be a red `Trash2` icon. Clicking it opens a confirmation popover; the
channel is deleted only after the user confirms.

The same interaction pattern applies to delete buttons inside the right member
list. Member deletion confirmation copy should state that the Agent itself will
not be deleted and that Agent memory will be updated.

## API Shape

Add channel member management endpoints:

- `POST /v1/channels/{id}/members`
- `DELETE /v1/channels/{id}/members/{agent_id}`

The add request accepts an `agentId` and uses the existing idempotency-key
pattern. The response returns the channel member record and may include a
`memoryStatus` field for immediate UI feedback. The remove response returns the
removed member id and the current member list.

Existing `GET /v1/channels/{id}/members` remains the source for the right-side
member list. Desktop should refresh members and channel messages after add/remove
operations.

## Data And Persistence

This design keeps channel membership in the existing channel service state. No
new membership snapshot table is added.

Memory update events should continue through `memory_update_events`. If needed,
new event types can distinguish:

- `channel_member_added`
- `channel_member_removed`
- `channel_join_report_requested`
- `channel_join_report_failed`

Visible join reports should be ordinary channel Agent messages created through
the message service, with stable idempotency so retries do not duplicate reports.

## Error Handling

- Adding a coordinator Agent returns `400 Bad Request`.
- Adding an Agent already in the channel returns the existing membership.
- Removing a coordinator Agent returns `400 Bad Request`.
- Removing a non-member returns `404 Not Found` or a no-op success only if an
  idempotency key proves it is a replay.
- Memory update failures set the affected member's readiness to `memory_failed`
  where the member still belongs to the channel.
- Removed-member memory update failures are diagnostic only because the member no
  longer appears in the channel.
- Join report runtime failures do not roll back readiness.

## Testing

Daemon tests should cover:

- only `agent_global_coordinator` is ensured for coordinator work
- per-channel coordinator Agents are no longer created for new channels
- coordinator prompt uses the current channel roster and excludes coordinators
- coordinator JSON validation rejects `agent_global_coordinator`
- adding a member triggers memory update and an Agent-authored join report
- removing a member updates removed and remaining members' memory without visible
  reports
- add/remove member endpoints reject coordinator Agents

Desktop tests should cover:

- Chat member button toggles the right member list and it is collapsed by default
- right member list excludes coordinator Agents
- add-member picker lists existing non-channel ordinary Agents only
- remove-member button is hidden until row hover/focus and uses a red trash icon
- remove-member confirmation popover appears before deletion
- channel sidebar delete button uses the same hover/focus, alignment, red icon,
  and confirmation popover behavior
- mention suggestions and DM lists exclude `agent_global_coordinator`

Verification commands:

- `cargo test -p slei-daemon channel`
- `cargo test -p slei-daemon coordinator`
- `pnpm --filter @slei/desktop test -- chat-channel-mentions.spec.tsx`
- `pnpm --filter @slei/desktop lint`
- `pnpm --filter @slei/desktop typecheck`
